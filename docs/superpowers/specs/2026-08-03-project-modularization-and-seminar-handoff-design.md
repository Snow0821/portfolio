# 프로젝트 모듈화 및 세미나 작성 시스템 핸드오프

## 1. 문서 목적

이 문서는 두 가지 후속 작업의 출발점이다.

1. 현재 프로젝트의 긴 파일과 중복 책임을 안전하게 모듈화한다.
2. 새 채팅에서 세미나 콘텐츠 규약, 에셋 관리, 검증과 결과물 생성 과정을 별도 시스템으로 설계한다.

이번 문서화 작업에서는 세미나 코드, 데이터와 스타일을 변경하지 않는다. 아래에서 `확정`은 현재 프로젝트 규칙으로 사용할 내용이고, `열린 결정`은 새 채팅에서 사용자 승인을 받아야 하는 내용이다.

## 2. 새 채팅에서 먼저 읽을 내용

새 채팅에서는 이 문서와 다음 파일을 먼저 검토한다.

- `AGENTS.md`: 작업 계획, 문제 해결 목록, 문서화와 검증 의무
- `docs/architecture.md`: 정적 사이트 원칙과 현재 의존 방향
- `docs/conventions.md`: 모듈 경계, 파일 크기와 모듈 문서 규칙
- `data/topics/python-intro.js`: 현재 슬라이드·읽기 문서 데이터 사례
- `components/slide-renderer.js`: 현재 발표 화면 렌더링 계약
- `components/document-renderer.js`: 현재 읽기 문서 렌더링 계약
- `services/pdf-exporter.js`: 현재 PDF와 인쇄 fallback 경계

새 채팅의 첫 작업은 코드를 수정하는 것이 아니라 이 문서의 열린 결정을 하나씩 확정하고 별도의 세미나 작성 시스템 설계 사양을 작성하는 것이다.

## 3. 확정된 프로젝트 원칙

### 3.1 기술 제약

- 프런트엔드는 빌드 없는 정적 HTML, CSS와 JavaScript ES module을 유지한다.
- Node.js는 자동 검증과 Vercel 로컬 실행에 사용하며 프런트엔드 컴파일을 필수화하지 않는다.
- 페이지는 조립, 컴포넌트는 UI, 서비스는 비-UI 기능, 데이터는 콘텐츠를 소유한다.
- 모든 변경은 관련 현재 문서와 연도별 이력을 같은 작업에서 갱신해야 완료된다.

### 3.2 작업 수행 방식

- 파일 변경 전에 목표, 수행 목록과 성공 기준을 먼저 정한다.
- 작업 중 발견한 문제는 `확인`, `해결`, `보류` 상태가 있는 해결 목록에 추가한다.
- 해결한 문제는 원인과 해결 방법을, 남은 문제는 다음 행동과 보류 이유를 기록한다.
- 사용자가 방법을 제안하면 수행 여부만 답하지 않고 기술적 의견, 이유와 trade-off를 함께 설명한다.

### 3.3 모듈화 기준

- 파일 수를 늘리는 것이 아니라 하나의 책임과 독립 변경·검증 가능성을 만드는 것이 목적이다.
- 실행 JavaScript, CSS와 테스트는 200줄 이하를 권장한다.
- 200줄을 넘으면 책임 분리를 검토하고 300줄을 넘으면 분리하거나 예외 근거를 남긴다.
- 일반 모듈화 후속 작업에서 300줄 기준과 예외 목록을 자동 검증에 추가한다.
- 콘텐츠 데이터, 문서, 이력과 생성 산출물은 줄 수 검사에서 제외한다.
- 복잡한 기능 묶음은 디렉터리 README로 책임, 공개 계약, 내부 파일, 의존 방향, 오류 처리, 테스트와 확장 규칙을 설명한다.
- 모든 파일에 별도 문서를 만들지 않으며 작은 공개 계약은 필요한 경우 JSDoc으로 설명한다.

## 4. 현재 모듈화 검수 결과

우선순위가 높은 대상은 다음과 같다.

| 대상 | 현재 문제 | 권장 경계 |
| --- | --- | --- |
| `tests/verify-structure.mjs` | 500줄 이상에 구조, 컴포넌트, 페이지, PDF 테스트와 fake DOM이 함께 있음 | 도메인별 테스트와 공용 `tests/helpers/` |
| `styles/components/presentation.css` | 400줄 이상에 헤더, 레이아웃, 슬라이드, 읽기 문서와 반응형 규칙이 함께 있음 | 헤더, 프레젠테이션 레이아웃, 슬라이드 카드, 읽기 문서 스타일 |
| HTML 문자열 렌더러 | 여러 컴포넌트에 이스케이프 함수가 중복됨 | 작은 공용 HTML 안전 유틸리티 |
| `services/pdf-exporter.js` | 임시 DOM 구성, 배치, 옵션과 내보내기 생명주기가 결합됨 | 렌더 영역과 내보내기 생명주기 경계 |

데이터 파일과 100줄 안팎의 응집된 controller는 줄 수만으로 분리하지 않는다. 구체적인 파일 이동과 공개 API는 일반 모듈화 구현 계획에서 테스트 우선으로 확정한다.

## 5. 세미나 작성 시스템의 확정된 목표

세미나는 단순한 데이터 객체가 아니라 콘텐츠 제작 시스템으로 발전시킨다.

- 모든 세미나가 공유하는 콘텐츠 계약과 작성 원칙을 제공한다.
- 각 세미나는 대상 독자, 목적, 핵심 메시지, 전체 맥락과 세부 내용을 구조적으로 표현한다.
- 제목, 본문, 목록, 코드, 인용, 요약과 이미지 같은 요소를 명시적인 콘텐츠 블록으로 다룬다.
- 이미지는 마크업에 임의 삽입하지 않고 경로와 접근성 정보를 포함하는 구조화된 에셋으로 다룬다.
- 구조화된 요소를 조합해 발표 슬라이드, 읽기 문서와 PDF 또는 인쇄 결과물을 만든다.
- 레이아웃의 시각적 안정성을 위해 콘텐츠 분량을 검증한다.
- 세미나 모듈은 작성 규약과 생성 과정을 설명하는 디렉터리 README를 가진다.

## 6. 권장하는 세미나 처리 흐름

아래 흐름은 현재까지의 기술적 권장안이며 세부 계약은 새 채팅에서 승인한다.

```text
세미나 맥락·메타데이터
        ↓
공통 개요와 구조화 콘텐츠 블록 + 이미지 에셋 명세
        ↓
스키마·접근성·분량·파일 존재 검증
        ↓
발표용/읽기용 표현 어댑터
        ↓
공용 렌더러와 스타일
        ↓
브라우저 화면 → PDF 또는 인쇄 fallback
```

권장안은 하나의 공통 원본을 중심으로 하되 발표와 읽기 자료가 필요한 블록만 모드별로 추가하거나 덮어쓰는 혼합형 모델이다. 완전한 단일 원본은 표현 차이를 억지로 없앨 수 있고, 완전히 분리된 원본은 현재의 중복을 유지하기 때문이다. 이 선택은 아직 사용자 승인 전이다.

## 7. 콘텐츠 분량과 시각 안정성 원칙

하나의 전역 글자 수 제한은 사용하지 않는 방향을 권장한다. 한글, 영문, 코드와 이미지의 실제 점유 면적이 다르기 때문이다.

- 레이아웃 또는 블록 종류별로 제목, 본문, 목록 개수, 항목 길이와 코드 줄 수 예산을 둔다.
- 권장 예산 초과는 작성자가 맥락을 유지하면서 수정할 수 있도록 경고로 보고한다.
- 필수 제목, 이미지 대체 텍스트와 존재하지 않는 에셋처럼 명백한 계약 위반은 오류로 처리한다.
- 브라우저 검증에서 실제 DOM overflow, 잘림과 가로 스크롤을 확인해 글자 수 검사의 한계를 보완한다.
- 정확한 수치와 경고·오류 경계는 실제 레이아웃 샘플을 비교한 뒤 정한다.

## 8. 이미지 에셋 방향

이미지 블록은 최소한 원본 경로와 대체 텍스트를 구조적으로 제공해야 한다. 캡션, 출처·라이선스, 종횡비, 맞춤 방식과 초점 위치는 권장 후보이며 새 채팅에서 필수 여부를 정한다.

검증기는 다음 문제를 탐지하는 방향을 권장한다.

- 존재하지 않는 로컬 파일
- 비어 있는 대체 텍스트
- 레이아웃과 맞지 않는 종횡비 또는 해상도
- 필요한 출처나 캡션 누락
- 동일 의미 이미지의 불필요한 중복

외부 URL 이미지는 가용성과 PDF 생성 안정성이 떨어질 수 있으므로 기본값은 저장소가 소유하는 로컬 에셋을 권장한다.

## 9. 새 채팅에서 확정할 열린 결정

다음 항목은 합의된 것처럼 구현하지 않는다.

1. 발표 슬라이드와 읽기 문서가 공통 원본을 공유하는 정확한 방식
2. 세미나 한 개의 디렉터리와 파일 구성
3. 지원할 콘텐츠 블록 종류와 각 블록의 필수 필드
4. 레이아웃별 콘텐츠 예산의 정확한 수치
5. 경고만 할 항목과 자동 테스트를 실패시킬 오류 항목
6. 이미지의 필수 메타데이터, 허용 비율, 해상도와 출처 정책
7. 브라우저 런타임 조립만 유지할지 정적 산출물 생성 단계를 추가할지 여부
8. 기존 `python-intro`와 `web-intro` 데이터를 새 계약으로 옮기는 호환 전략

현재 프로젝트의 빌드 없는 정적 사이트 결정은 유효하다. 정적 산출물 생성 단계를 추가하려면 별도의 장기 결정 변경이 필요하다.

## 10. 새 채팅의 권장 진행 순서

1. 공통 원본과 모드별 표현의 관계를 결정한다.
2. 하나의 실제 세미나를 기준으로 최소 콘텐츠 블록과 에셋 계약을 설계한다.
3. 레이아웃별 콘텐츠 예산과 검증 심각도를 정한다.
4. 목표 디렉터리, 공개 API와 의존 방향을 설계한다.
5. 기존 두 세미나의 마이그레이션과 호환 범위를 정한다.
6. 설계 사양을 승인한 뒤 테스트 우선 구현 계획을 작성한다.

## 11. 완료 기준

이 핸드오프의 완료 기준은 세미나 구현이 아니라 다음 상태다.

- 새 채팅이 현재 제약과 확정된 목표를 코드 추측 없이 이해할 수 있다.
- 권장안과 사용자 승인이 필요한 열린 결정이 섞여 있지 않다.
- 일반 모듈화 작업과 세미나 작성 시스템 구현이 별도 작업으로 구분된다.
- README와 현재 문서에서 이 핸드오프를 찾을 수 있다.
