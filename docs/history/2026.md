## 2026-08-03 — 페이지·컴포넌트 중심 구조 설계

### 요청과 목적

- `index.html`을 제외한 화면을 명시적인 페이지 패키지로 구성한다.
- 페이지 모듈은 조립에 집중하고 실제 구현은 컴포넌트 중심으로 구성한다.
- CSS는 가능한 한 공통 계층을 공유한다.
- 모든 변경 작업에 문서화와 작업 이력이 동반되도록 강제한다.
- 현재 구조와 과거 변경 과정을 각각 쉽게 찾을 수 있는 문서 체계를 만든다.

### 파악한 문제

- `level1-*`부터 `level4-*`까지의 디렉터리명이 책임보다 추상적인 계층을 표현한다.
- 페이지 초기화 코드가 HTML 안에 포함되어 있고 공용 컴포넌트와 페이지 전용 코드가 혼재한다.
- 세미나 콘텐츠와 리다이렉트 페이지가 중복되어 단일 출처가 불명확하다.
- 기존 구조 검증 스크립트가 삭제된 CSS 경로를 계속 요구한다.
- 프로젝트 구조, 구현 철학, 현재 문제와 과거 결정의 공식 기록 위치가 없다.

### 결정과 근거

- 빌드 도구 없이 동작하는 페이지 패키지 구조를 선택했다.
- 공용 UI는 `components/`, UI가 아닌 기능은 `services/`, 정적 콘텐츠는 `content/`로 분리한다.
- CSS는 `tokens → base → layouts → components → page.css` 순서로 의존한다.
- 현재 사실은 `architecture.md`, `conventions.md`, `decisions.md`, `status.md`에서 유지하고 변경 과정은 연도별 이력에 기록한다.
- 작업별 로그와 개별 ADR 파일은 현재 규모에 비해 관리 비용이 크므로 만들지 않는다.
- 프로젝트 파일을 변경한 작업은 관련 현재 문서와 이력을 함께 갱신해야 완료된 것으로 간주한다.
- 검증 스크립트는 현재 환경에 없는 Node나 PowerShell 대신 사용 가능한 Python 3 표준 라이브러리로 작성한다.

### 수행한 작업

## 2026-08-03 — Vercel 로컬 개발 환경 설계 보완

### 요청과 목적

- Vercel에 코드를 올리기 전에 정적 페이지와 향후 API를 로컬에서 함께 확인한다.
- 로컬 시스템에 Node.js를 직접 설치하지 않고 개발·검증 버전을 통일한다.
- 향후 API 기능을 같은 저장소 안에서 자연스럽게 확장할 수 있게 한다.

### 파악한 문제

- 현재 로컬 환경에는 Node와 PowerShell이 없어 기존 계획의 JavaScript 또는 PowerShell 검증기를 직접 실행할 수 없다.
- Python 정적 서버는 HTML·CSS·클라이언트 JavaScript를 제공할 수 있지만 Vercel Functions 실행 환경을 재현하지 못한다.
- Vercel 배포용 컨테이너를 도입하면 정적 사이트와 작은 Functions에 비해 운영 모델이 불필요하게 복잡해진다.

### 결정과 근거

- Docker는 운영 배포물이 아니라 로컬 개발과 검증 환경으로만 사용한다.
- Docker 안에 Vercel 기본 런타임과 맞춘 Node.js 24 및 Vercel CLI를 설치한다.
- 이 결정은 같은 날 앞서 계획한 로컬 Python 구조 검증기를 Docker 내부 Node.js 검증기로 대체한다.
- 로컬 통합 실행은 Vercel 공식 개발 명령인 `vercel dev`를 사용한다.
- 프런트엔드는 빌드 없는 정적 구조를 유지하고 API만 `api/*.mjs` Vercel Functions로 확장한다.
- 실제 프런트엔드 번들링 요구가 생기기 전에는 Vite를 도입하지 않는다.
- 운영과 Preview 배포는 기존 Git→Vercel 흐름을 유지하고 `Dockerfile.vercel`은 만들지 않는다.

### 수행한 작업

- `docker --version`과 `docker compose version`으로 로컬 Docker 사용 가능 여부를 확인했다.
- Docker 기반 개발 환경, `/api/health`, Node 구조 검증기를 목표 구조와 검증 기준에 추가했다.

### 검증 결과

- Docker 29.5.3과 Docker Compose 5.1.4를 사용할 수 있음을 확인했다.
- 저장소에 기존 `.vercel`, `vercel.json`, `package.json`, lockfile이 없음을 확인했다.

### 남은 작업

- 수정된 설계를 반영해 `docs/plan.md`의 Python 검증 단계를 Docker/Node 검증 단계로 교체한다.
- Docker 개발 환경, Node 도구 체인과 health function을 구현한다.
- Vercel 계정 연결이 필요한 로컬 Functions 및 Preview 검증은 사용자 승인 범위 안에서 수행한다.

## 2026-08-03 — fnm 기반 개발 환경으로 경량화

### 요청과 목적

- Docker 컨테이너 안에서 상시 개발할 때 생기는 실행과 디버깅 마찰을 피한다.
- Homebrew를 사용하지 않고 프로젝트별 Node.js 버전을 관리한다.
- 새 작업자가 동일한 개발 환경을 준비할 수 있도록 기본 설치와 사용법을 README에 기록한다.

### 파악한 문제

- Docker는 현재 정적 프런트엔드와 소규모 Vercel Functions에 비해 개발 환경이 무겁다.
- Homebrew는 사용자 환경에서 기존 도구와 충돌한 경험이 있어 설치 경로로 사용할 수 없다.
- `fnm` 바이너리는 `~/.local/bin/fnm`에 설치되었지만 셸 `PATH` 설정은 사용자가 명시적으로 관리해야 한다.

### 결정과 근거

- 같은 날 작성한 개발 전용 Docker 설계를 철회하고 `fnm` 기반 Node.js 24 환경으로 대체한다.
- `fnm`은 Homebrew 없이 `~/.local/bin`에 설치하고 zsh 초기화 두 줄만 사용자가 관리한다.
- Node.js 버전은 `.node-version`, Vercel CLI와 JavaScript 의존성은 프로젝트 `package.json`과 lockfile로 고정한다.
- Python 정적 서버는 Node/Vercel 도구가 구성되기 전까지의 단순 페이지 확인 방법으로 유지한다.

### 수행한 작업

- `README.md`에 Homebrew 없는 `fnm` 설치, zsh 연결, Node.js 24 설치와 확인 방법을 기록했다.
- 현재 실행 가능한 Python 정적 서버와 향후 `npm run dev`, `npm test` 흐름을 구분해 기록했다.
- `docs/architecture.md`와 `docs/status.md`에서 Docker 개발 환경을 `fnm` 기반 환경으로 정정했다.
- `docs/plan.md`의 Python 검증 계획을 Node.js 구조 검증과 Vercel Functions 기반으로 갱신했다.

### 검증 결과

- `~/.local/bin/fnm`에서 fnm 1.39.0이 실행되는 것을 확인했다.
- fnm에 Node.js v24.18.1이 기본 버전으로 설치된 것을 확인했다.
- 프로젝트 루트의 사용자 생성 `.node-version` 값이 `24`인 것을 확인했다.
- README 명령이 현재 파일 상태와 앞으로 추가될 `package.json` 상태를 혼동하지 않도록 구분했으며 Markdown 공백 검사를 수행했다.

## 2026-08-03 — Node/Vercel 개발 기반과 문서 가드레일 적용

### 요청과 목적

- 승인된 구조 개편 계획의 첫 단계로 로컬 실행, API 확장과 자동 검증 기반을 만든다.
- 모든 프로젝트 변경에 현재 문서와 연도별 작업 이력을 동반하는 규칙을 저장소 수준에서 명시한다.

### 파악한 문제

- 프로젝트에 `package.json`, lockfile과 자동 검증기가 없어 Node 및 Vercel CLI 버전과 검증 명령이 고정되지 않았다.
- Vercel Functions의 로컬·Preview 동작을 확인할 최소 API가 없었다.
- 문서화 원칙이 설계 문서에만 있고 이후 작업자가 즉시 발견할 루트 작업 규칙이 없었다.
- Vercel CLI 58.4.4 설치 결과 전이 의존성에서 30개 감사 항목과 `tar`, `stream-to-promise` 사용 중단 경고가 보고됐다.

### 결정과 근거

- `.node-version`과 `package.json#engines.node`를 Node.js 24로 맞추고 Vercel CLI 58.4.4를 개발 의존성으로 고정했다.
- 자동 검증은 추가 프레임워크 없이 Node 표준 테스트 러너를 사용한다.
- 루트 `AGENTS.md`에 문서화, 구조, 개발 환경과 완료 전 검증 규칙을 두고 상세 규칙은 `docs/conventions.md`에서 관리한다.
- 전이 의존성 경고는 강제 업그레이드로 lockfile을 불안정하게 바꾸지 않고 현재 리스크로 기록해 상위 Vercel CLI 갱신 시 재검토한다.

### 수행한 작업

- `.gitignore`, `package.json`, `package-lock.json`과 `tests/verify-structure.mjs`를 추가했다.
- 프로젝트 로컬 `vercel dev`와 Node 표준 테스트 명령을 npm 스크립트로 제공했다.
- HTTP 200과 `{ "status": "ok" }`를 반환하는 `api/health.mjs`를 추가했다.
- `AGENTS.md`, `docs/conventions.md`, `docs/decisions.md`를 추가하고 README의 설치 및 실행 흐름을 현재 상태로 갱신했다.

### 검증 결과

- 구현 전에 구조 검증 테스트를 실행해 개발·문서 파일과 health function이 없어서 실패하는 것을 확인했다.
- `npm install`로 278개 패키지를 설치하고 lockfile을 생성했다.
- `npm test`에서 필수 파일, Node.js 24 메타데이터와 health function 응답을 검증하는 테스트 3개가 모두 통과했다.

- zsh 로그인 환경에서 fnm 1.39.0, Node.js v24.18.1과 npm 11.16.0을 확인했다.

## 2026-08-03 — PDF 내보내기 서비스와 정리 보장

### 요청과 목적

- 세미나 목록 renderer에 섞여 있던 PDF용 DOM과 내보내기 로직을 비-UI 서비스로 분리한다.
- 실제 viewer와 동일한 가로 컨테이너 구조를 사용하고 성공, fallback과 예외 모든 경로에서 임시 DOM을 제거한다.
- PDF 엔진을 사용할 수 없는 환경에서도 현재 주제와 형식을 유지한 인쇄 화면을 제공한다.

### 파악한 문제

- 기존 가로 PDF 경로는 `.slide-container.horizontal` 요소를 직접 만들지 않아 카드 배치 보정 코드가 적용될 대상이 없었다.
- 임시 DOM 제거가 성공 경로의 `try` 끝에만 있어 exporter가 throw하면 요소가 문서에 남았다.
- PDF 상태 UI와 renderer, 데이터 선택, 내보내기 옵션 및 fallback URL이 한 컴포넌트에 결합돼 있었다.
- 로컬 Chrome 검증 환경에서는 외부 CDN의 `html2pdf` 전역이 로드되지 않아 직접 다운로드 대신 fallback이 필요한 상태였다.

### 결정과 근거

- `services/pdf-exporter.js`가 렌더 영역 생성, A4 옵션, 내보내기와 `finally` 정리를 단독 소유한다.
- renderer는 callback으로 주입하고 서비스는 presentation URL이나 페이지 모듈을 알지 못하게 했다.
- 가로 대상은 실제 `.slide-container.horizontal` 구조로 만들고 1024×724 비율과 카드별 page break를 적용했다.
- `html2pdf`가 없으면 페이지가 주제와 모드를 유지한 `print=true` URL을 새 탭으로 연다.
- 버튼의 disabled, loading과 아이콘 복구는 목록 컴포넌트가 callback 결과와 관계없이 보장한다.

### 수행한 작업

- `createPdfRenderZone`, `createPdfOptions`, `exportSeminarPdf`를 제공하는 PDF 서비스를 추가했다.
- 세미나 페이지에 기존 `html2pdf` CDN 엔진과 PDF 서비스를 연결하고 읽기·발표 renderer를 mode에 따라 주입했다.
- `createPrintFallbackUrl`로 현재 topic과 mode를 보존하는 인쇄 URL을 한 곳에서 생성했다.
- 세미나 목록 컴포넌트에 다운로드 중 버튼 잠금, 로딩 표시와 `finally` 복구를 추가했다.
- 클라이언트 PDF와 인쇄 fallback의 장기 결정을 `docs/decisions.md`에 기록했다.

### 검증 결과

- 구현 전에 PDF 서비스와 fallback URL export가 없어 서비스 계약 테스트가 실패하는 것을 확인했다.
- `npm test`에서 가로 렌더 구조와 카드 5개, page break, exporter 의도적 실패 후 정리, 엔진 부재 fallback 및 URL 보존을 포함한 테스트 9개가 모두 통과했다.
- 버튼 callback이 진행 중일 때 disabled와 loading 상태를 사용하고 완료 후 원래 아이콘과 상태로 복구되는 것을 자동 검증했다.
- 실제 Chrome 브라우저용 임시 하네스에서 가로 target 1개와 카드 5개를 확인했다.
- 브라우저 exporter를 의도적으로 throw한 후와 fallback 실행 후 `#pdf-temp-render-zone`이 각각 0개이고 콘솔 오류가 없음을 확인한 뒤 임시 하네스를 제거했다.
- 로컬 브라우저에서 CDN 엔진이 로드되지 않은 상태를 확인했으며 이 경우 인쇄 fallback이 호출되는 것을 확인했다.
- `git diff --check`가 공백 오류 없이 통과했다.

### 남은 작업

- 구 세미나·프레젠테이션 코드와 CSS, 중복 콘텐츠 및 과거 로그 디렉터리를 제거한다.
- 최종 Vercel 통합 검증에서 CDN 사용 가능 여부와 `/api/health`를 다시 확인한다.

## 2026-08-03 — Vercel 개발 명령 재귀 오류 수정

### 요청과 목적

- 프로젝트 연결 후 `npm run dev`가 재귀 실행 오류로 종료되는 원인을 파악하고 로컬 정적 화면과 Functions 통합 실행을 복구한다.

### 파악한 문제

- 기존 `package.json#scripts.dev` 값이 `vercel dev --listen 3000`이었다.
- Vercel CLI 58.4.4는 실행 초기에 `scripts.dev`가 `vercel dev`를 포함하는지 검사하고, 포함하면 Development Command로 다시 호출될 가능성이 있다고 판단해 즉시 중단한다.
- 연결된 프로젝트는 Framework Preset이 `Other`이고 원격 Development Command override가 없었으므로 원격 설정이 아니라 로컬 npm 스크립트 이름이 직접 원인이었다.

### 결정과 근거

- Vercel CLI의 예약 검사 대상인 `dev` 스크립트를 제거하고 같은 명령을 `dev:vercel`로 제공한다.
- 별도 정적 서버나 프레임워크를 추가하지 않고 Vercel의 `Other` preset 기본 정적 파일 처리를 그대로 사용한다.
- 이 충돌이 돌아오지 않도록 `scripts.dev` 부재와 `scripts.dev:vercel` 값을 자동 테스트로 고정한다.

### 수행한 작업

- `package.json`의 로컬 통합 명령을 `npm run dev:vercel`로 변경했다.
- README, 작업 규칙, 구조·규칙·결정·상태 문서의 현재 명령을 함께 갱신했다.
- Vercel 로컬 실행 스크립트의 재귀 방지 회귀 테스트를 추가했다.

### 검증 결과

- 수정 전에 동일한 `npm run dev` 오류를 재현하고 새 회귀 테스트가 기존 `scripts.dev` 값 때문에 실패하는 것을 확인했다.
- `npx vercel project inspect portfolio`로 Framework Preset `Other`, Node.js 24.x와 별도 Development Command override 부재를 확인했다.
- 수정 후 자동 테스트 12개가 모두 통과했다.
- `npm run dev:vercel`이 Vercel CLI 58.4.4와 Node.js v24.18.1에서 재귀 오류 없이 `http://localhost:3000`을 시작했다.
- Vercel 로컬 서버를 통해 홈이 HTTP 200, `/api/health`가 HTTP 200과 `{ "status": "ok" }`를 반환하는 것을 확인했다.

### 남은 작업

- 실제 배포를 시작할 때 Vercel Preview에서 전체 화면과 `/api/health`를 다시 검증한다.

## 2026-08-03 — 모듈화 규칙과 세미나 작성 시스템 핸드오프

### 요청과 목적

- 프로젝트를 다시 검수해 긴 파일과 복잡한 책임을 줄일 모듈화 기준을 정한다.
- 모든 작업에서 계획을 먼저 정하고 발견한 문제를 해결 목록으로 관리하며, 사용자 제안에는 독립적인 의견을 함께 제시하는 규칙을 저장소에 남긴다.
- 세미나 작성 시스템은 새 채팅에서 구현할 수 있도록 지금까지 확정된 목표와 열린 결정을 구분해 전달한다.

### 최초 작업 목록

1. 현재 파일 크기, 책임과 중복 구현을 검수한다.
2. 모듈 크기와 선택적 문서화 기준을 현재 규칙에 반영한다.
3. 세미나 작성 시스템의 확정 사항과 열린 결정을 분리한다.
4. 새 채팅용 설계 핸드오프를 만들고 README와 현재 문서에서 연결한다.
5. 자동 테스트와 문서 검증을 수행한다.

### 문제와 해결 목록

- `해결`: 줄 수만으로 파일을 나누면 작은 파일이 과도하게 늘 수 있다. 한 책임, 독립 변경과 독립 검증 가능성을 우선 기준으로 정하고 200줄 권장·300줄 검토 기준을 보조 가드레일로 채택했다.
- `해결`: 모든 모듈에 별도 문서를 두면 코드와 문서가 쉽게 어긋날 수 있다. 복잡한 기능 디렉터리만 README를 두고 작은 계약은 JSDoc으로 설명하도록 범위를 제한했다.
- `확인`: 통합 테스트와 프레젠테이션 CSS가 300줄을 넘고 HTML 이스케이프가 여러 렌더러에 중복되어 있다. 이번 작업은 설계 문서화로 제한하고 실제 분리는 일반 모듈화 후속 작업으로 남겼다.
- `확인`: PDF 서비스에 임시 DOM 구성과 내보내기 옵션이 함께 있다. 렌더 영역과 내보내기 생명주기를 우선 분리 후보로 기록했다.
- `보류`: 세미나 슬라이드와 읽기 자료의 공통 원본 방식, 정확한 콘텐츠 예산과 이미지 메타데이터는 사용자 승인이 필요하다. 새 채팅의 열린 결정 목록으로 이동했다.
- `해결`: 비대화형 검증 셸의 `PATH`에 `npm`이 없어 첫 테스트 명령을 실행하지 못했다. 설치된 fnm의 Node.js 24 환경을 명시하는 `/Users/snow0821/.local/bin/fnm exec --using=24 npm test`로 다시 실행했다.
- `해결`: 자체 검토에서 아직 구현하지 않은 파일 길이 자동 검증이 현재 동작하는 것처럼 읽히는 문구와 기존 결정 상태의 잘못된 변경을 발견했다. 자동화는 후속 작업임을 명시하고 기존 상태를 복원했다.

### 결정과 근거

- 실행 JavaScript, CSS와 테스트는 200줄 이하를 권장하고 300줄을 넘으면 분리하거나 예외 근거를 남긴다. 자동 검증은 일반 모듈화 후속 작업에서 추가한다.
- 파일이 세 개 이상이거나 공개 계약, 생명주기 또는 의존 방향이 복잡한 기능만 디렉터리 README를 둔다.
- 작업 전 계획, 작업 중 문제 상태, 완료 후 해결과 검증을 하나의 작업 주기로 만들고 사용자 제안에는 기술적 의견과 trade-off를 포함한다.
- 세미나는 공통 규약, 맥락, 세부 콘텐츠, 구조화 이미지, 검증과 결과물 생성이 연결된 작성 시스템으로 다룬다.
