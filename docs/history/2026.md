# 2026 Work History

## 2026-08-03 — 페이지·컴포넌트 중심 구조 설계

### 요청과 목적

- `index.html`을 제외한 화면을 명시적인 페이지 패키지로 구성한다.
- 페이지 모듈은 조립에 집중하고 실제 구현은 컴포넌트 중심으로 구성한다.
- CSS는 가능한 한 공통 계층을 공유한다.
- 모든 변경 작업에 문서화와 작업 이력이 동반되도록 강제한다.
- 현재 구조와 과거 변경 과정을 각각 쉽게 찾을 수 있는 문서 체계를 만든다.

### 파악한 문제

- `level1-*`부터 `level4-*`까지의 디렉터리명이 책임보다 추상적인 계층을 표현한다.
- 페이지 초기화 코드가 HTML 안에 포함되어 있고 공용 컴포넌트와 페이지 전용 코드가 혼재한다.
- 세미나 콘텐츠와 리다이렉트 페이지가 중복되어 단일 출처가 불명확하다.
- 기존 구조 검증 스크립트가 삭제된 CSS 경로를 계속 요구한다.
- 프로젝트 구조, 구현 철학, 현재 문제와 과거 결정의 공식 기록 위치가 없다.

### 결정과 근거

- 빌드 도구 없이 동작하는 페이지 패키지 구조를 선택했다.
- 공용 UI는 `components/`, UI가 아닌 기능은 `services/`, 정적 콘텐츠는 `content/`로 분리한다.
- CSS는 `tokens → base → layouts → components → page.css` 순서로 의존한다.
- 현재 사실은 `architecture.md`, `conventions.md`, `decisions.md`, `status.md`에서 유지하고 변경 과정은 연도별 이력에 기록한다.
- 작업별 로그와 개별 ADR 파일은 현재 규모에 비해 관리 비용이 크므로 만들지 않는다.
- 프로젝트 파일을 변경한 작업은 관련 현재 문서와 이력을 함께 갱신해야 완료된 것으로 간주한다.
- 검증 스크립트는 현재 환경에 없는 Node나 PowerShell 대신 사용 가능한 Python 3 표준 라이브러리로 작성한다.

### 수행한 작업

- 승인된 목표 구조와 원칙을 `docs/architecture.md`에 문서화했다.
- 구조 개편의 검증 기준과 문서 유지 전략을 명시했다.
- 설계 단계의 작업 이력을 이 문서에 기록했다.
- 구현 전 현재 상태와 다음 단계를 `docs/status.md`에 기록했다.
- 사용자 설계 승인 후 파일별 책임, 테스트 우선 순서, 커밋 경계를 포함한 실행 계획을 `docs/plan.md`에 작성했다.

### 검증 결과

- 설계 문서에서 `TBD`, `TODO`, 미정 요구사항을 검색했다.
- 목표 구조, 의존 방향, URL 정책, 초기 개편 범위와 검증 기준 사이의 모순이 없는지 확인했다.
- Markdown 공백 오류를 `git diff --check`로 확인했다.
- `command -v node`, `command -v pwsh`, `command -v python3`과 각 버전 확인으로 검증기 실행 환경을 조사했다. Node와 PowerShell은 없고 Python 3.14.3을 사용할 수 있음을 확인했다.
- 구현 계획에서 승인된 설계 요구사항이 각 작업과 최종 성공 기준에 연결되는지 검토하고, 미래 작업에 대한 선행 의존성이 없도록 작업 인터페이스를 정정했다.

### 남은 작업

- `docs/plan.md`의 작업 순서에 따라 구조 개편과 동작 문제 수정을 구현한다.
- 각 작업에서 자동 검증, 필요한 브라우저 검증과 문서 갱신을 함께 수행한다.

## 2026-08-03 — Vercel 로컬 개발 환경 설계 보완

### 요청과 목적

- Vercel에 코드를 올리기 전에 정적 페이지와 향후 API를 로컬에서 함께 확인한다.
- 로컬 시스템에 Node.js를 직접 설치하지 않고 개발·검증 버전을 통일한다.
- 향후 API 기능을 같은 저장소 안에서 자연스럽게 확장할 수 있게 한다.

### 파악한 문제

- 현재 로컬 환경에는 Node와 PowerShell이 없어 기존 계획의 JavaScript 또는 PowerShell 검증기를 직접 실행할 수 없다.
- Python 정적 서버는 HTML·CSS·클라이언트 JavaScript를 제공할 수 있지만 Vercel Functions 실행 환경을 재현하지 못한다.
- Vercel 배포용 컨테이너를 도입하면 정적 사이트와 작은 Functions에 비해 운영 모델이 불필요하게 복잡해진다.

### 결정과 근거

- Docker는 운영 배포물이 아니라 로컬 개발과 검증 환경으로만 사용한다.
- Docker 안에 Vercel 기본 런타임과 맞춘 Node.js 24 및 Vercel CLI를 설치한다.
- 이 결정은 같은 날 앞서 계획한 로컬 Python 구조 검증기를 Docker 내부 Node.js 검증기로 대체한다.
- 로컬 통합 실행은 Vercel 공식 개발 명령인 `vercel dev`를 사용한다.
- 프런트엔드는 빌드 없는 정적 구조를 유지하고 API만 `api/*.mjs` Vercel Functions로 확장한다.
- 실제 프런트엔드 번들링 요구가 생기기 전에는 Vite를 도입하지 않는다.
- 운영과 Preview 배포는 기존 Git→Vercel 흐름을 유지하고 `Dockerfile.vercel`은 만들지 않는다.

### 수행한 작업

- `docker --version`과 `docker compose version`으로 로컬 Docker 사용 가능 여부를 확인했다.
- Docker 기반 개발 환경, `/api/health`, Node 구조 검증기를 목표 구조와 검증 기준에 추가했다.

### 검증 결과

- Docker 29.5.3과 Docker Compose 5.1.4를 사용할 수 있음을 확인했다.
- 저장소에 기존 `.vercel`, `vercel.json`, `package.json`, lockfile이 없음을 확인했다.

### 남은 작업

- 수정된 설계를 반영해 `docs/plan.md`의 Python 검증 단계를 Docker/Node 검증 단계로 교체한다.
- Docker 개발 환경, Node 도구 체인과 health function을 구현한다.
- Vercel 계정 연결이 필요한 로컬 Functions 및 Preview 검증은 사용자 승인 범위 안에서 수행한다.
