# Current Decisions

## D-001 — 페이지 패키지 구조

- 상태: 적용
- 결정: 루트 `index.html` 외의 사용자 화면은 `pages/` 아래에 HTML, 초기화 JavaScript와 페이지 CSS를 함께 둔다.
- 이유: URL 진입점과 화면 전용 책임을 빠르게 찾고 공용 컴포넌트와 분리하기 위해서다.

## D-002 — 공통 CSS 계층

- 상태: 적용
- 결정: CSS는 `tokens → base → layouts → components → page.css` 순으로 의존한다.
- 이유: 페이지별 중복을 줄이고 공통 시각 언어를 유지하기 위해서다.

## D-003 — 현재 문서와 연도별 이력

- 상태: 적용
- 결정: 현재 사실은 네 개의 현재 문서에 유지하고 변경 과정은 `docs/history/<year>.md`에 기록한다.
- 이유: 최신 정보를 쉽게 찾으면서 작업과 결정의 배경도 보존하기 위해서다.

## D-004 — fnm과 Node.js 구조 검증기

- 상태: 적용
- 결정: Homebrew와 Docker 대신 `fnm`, `.node-version`과 `package.json`으로 Node.js 24를 선택하고 Node 표준 테스트 러너를 사용한다.
- 이유: 로컬 환경 충돌과 컨테이너 개발 마찰을 피하면서 Vercel 런타임과 개발 버전을 맞추기 위해서다.

## D-005 — Vercel Functions

- 상태: 적용
- 결정: 서버 기능은 루트 `api/*.mjs` Vercel Functions로 만들고 Vercel CLI는 프로젝트 의존성으로 고정하며 로컬 통합은 `npm run dev:vercel`로 실행한다.
- 이유: 정적 프런트엔드를 유지하면서 동일 저장소에서 API를 확장하고 로컬 통합 실행을 제공하기 위해서다.

## D-006 — 클라이언트 PDF 생성

- 상태: D-010의 수동 정적 PDF 정책으로 대체
- 결정: 클릭 시점의 클라이언트 생성과 자동 인쇄 fallback은 사용하지 않는다.
- 이유: 외부 런타임과 팝업 정책에 따라 성공 여부가 달라져 사용자에게 신뢰할 수 있는 다운로드 계약을 제공하지 못했기 때문이다.

## D-007 — 책임 기반 모듈 크기와 선택적 문서화

- 상태: 적용
- 결정: 실행 코드, CSS와 테스트는 200줄 이하를 기본으로 하고 201~300줄은 경로와 이유가 기록된 예외만 허용하며 300줄 초과는 허용하지 않는다. 파일 길이와 로컬 ES module 참조는 자동 테스트로 검증한다.
- 결정: 파일 수를 늘리는 것 자체를 목표로 하지 않고 책임, 독립 변경과 독립 검증 가능성을 분리 기준으로 삼는다.
- 결정: 파일이 세 개 이상이거나 공개 계약·생명주기·의존 관계가 복잡한 기능만 디렉터리 README를 두고, 단순 파일은 필요한 JSDoc으로 설명한다.
- 이유: 긴 파일의 인지 부담을 줄이되 과도한 분할과 중복 문서의 유지 비용을 피하기 위해서다.

## D-008 — 계획·문제 해결·의견을 포함하는 작업 주기

- 상태: 적용
- 결정: 모든 변경 작업은 작업 목록과 성공 기준을 먼저 정하고, 발견한 문제를 상태가 있는 해결 목록으로 관리한 뒤 계획·문제·해결·검증을 연도별 이력에 보존한다.
- 결정: 사용자의 제안에는 실행 여부뿐 아니라 독립적인 기술 의견, 이유와 주요 trade-off를 함께 제시한다.
- 결정: 현재 성공 기준에 필요하지 않은 문제와 개선안은 근거와 영향을 아카이빙하고 다음 작업 시작 시 사용자와 검토한다. 보안, 데이터 손실과 현재 작업을 막는 회귀만 즉시 처리한다.
- 이유: 무엇을 왜 변경했는지 추적하고, 해결되지 않은 문제나 설계상의 우려가 동의 표현 뒤에 가려지지 않게 하기 위해서다.

## D-009 — 정규 문서 기반의 지속 가능한 작업 인계

- 상태: 적용
- 결정: 프로젝트의 현재 상태는 README, AGENTS, 네 개의 현재 문서와 필요한 모듈 README만으로 이해할 수 있게 유지한다.
- 결정: 작업 중 임시 설계와 구현 계획을 사용할 수 있지만 완료 시 보편적인 내용은 현재 문서, 수행 과정은 연도별 이력에 흡수하고 임시 문서는 제거한다.
- 이유: 대화별 문서가 누적되거나 낡아 현재 정보와 충돌하는 일을 막으면서 새 작업이 특정 대화 기록에 의존하지 않게 하기 위해서다.

## D-010 — 세미나 기능 패키지와 `60분 개론형`

- 상태: 적용
- 결정: 세미나 전용 데이터, UI, 레이아웃, 에셋, 스타일과 테스트는 `features/seminars/`가 소유하고 `pages/`에는 기존 URL 진입과 초기 조립만 남긴다.
- 결정: 전역에는 실제 비세미나 소비자가 있는 사이트 공통 모듈만 두며, 미래의 재사용 가능성만으로 세미나 구현을 미리 공통화하지 않는다.
- 결정: 첫 형식인 `introductory-60`은 비전공자 일반인을 대상으로 `문제의 정의 → 기존 접근 → 핵심 방법론 → 활용 사례 → 결론과 한계`의 의미 구조를 사용한다. 화면 제목은 쉽게 바꿀 수 있고 핵심 방법론을 중심에 두되 나머지 단계도 필수 맥락으로 유지한다.
- 결정: `60분`은 분량 제한이 아니며, 하나의 구조화 원본에서 발표용 슬라이드와 독립적으로 읽히는 자료를 만든다.
- 결정: 런타임은 두 HTML 표현만 제공한다. PDF는 사용자가 수동 인쇄·시각 검토한 네 정적 파일을 전달할 때까지 보류하고, 실제 파일이 없는 다운로드 링크는 공개하지 않는다.
- 결정: 공통·주제별 의도는 `discussions/`에서 먼저 논의하고, 합의된 결정만 `formats/` 또는 `data/topics/`에 반영한다. 논의 문서는 런타임 소스가 아니다.
- 결정: 두 HTML 자료는 새 탭에 자료만 표시하며 사이트 헤더, 모드·뒤로·돌아가기 링크, 슬라이드 버튼과 카운터를 두지 않는다. 발표의 방향키·Space·스크롤·터치 이동은 유지한다.
- 이유: 세미나 규약과 변경 이유가 같은 구현을 한 경계에서 발전시키고, 발표 시간 때문에 자료의 완결성이 훼손되거나 두 표현의 내용이 어긋나는 일을 막기 위해서다.

## D-011 — main 직접 작업과 간결한 검증

- 상태: 적용
- 결정: 사용자가 별도 브랜치나 worktree를 요청하지 않으면 `main`에서 직접 작업한다.
- 결정: 반복 중에는 변경 유형별 가까운 테스트 그룹을 사용하고, UI가 안정된 뒤 브라우저 행렬 한 번과 최종 `npm run verify` 한 번을 실행한다.
- 결정: 같은 접근의 세 번째 시도와 30분 이상 결과 없는 진행을 피하고, 방향 변경 시 폐기된 코드·테스트·계획을 즉시 제거하며 하나의 응집된 구현 커밋을 우선한다.
- 이유: 빠른 자동 검증의 품질은 유지하면서 worktree 정리, 반복 리뷰, 전체 브라우저 행렬과 미세 커밋이 만드는 작업 지연을 줄이기 위해서다.
