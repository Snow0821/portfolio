# Seminar Domain Package Design

## 1. 상태와 범위

- 상태: 사용자 승인, 구현 계획 승인, 격리 worktree에서 구현 시작
- 승인일: 2026-08-03
- 범위: 세미나 전용 구현의 소유 경계와 첫 형식인 `introductory-60`의 작성·표현·검증 계약
- 후속 작업: 승인된 구현 계획에 따라 기존 세미나 기능과 두 주제를 새 구조로 이전한다.

이 문서는 여러 세션에 걸치는 구조 이전을 위한 임시 설계 사양이다. 구현이 끝나면 보편적인 내용은 `features/seminars/README.md`, 형식 규약과 전역 현재 문서에 흡수하고 수행 과정은 `docs/history/2026.md`에 보존한 뒤 이 문서를 제거한다.

## 2. 목표

1. 세미나 전용 데이터, UI, 레이아웃, 에셋, PDF·인쇄 기능, 스타일과 테스트를 하나의 기능 패키지가 소유한다.
2. 페이지 진입점과 사이트 전체 공통 모듈의 책임을 세미나 도메인에서 분리한다.
3. 비전공자 일반인을 위한 `60분 개론형` 세미나의 공통 서사와 자료 품질을 정의한다.
4. 하나의 구조화 원본에서 발표용 슬라이드와 독립적으로 읽히는 문서를 만든다.
5. 내용의 완결성을 발표 시간이나 정량적인 분량 제한보다 우선한다.
6. 실제 세미나 제작 경험을 근거로 규약을 점진적으로 개선할 수 있게 한다.

## 3. 비목표

- 이번 설계 단계에서는 실행 파일을 이동하거나 기존 데이터를 변환하지 않는다.
- 기존 공개 URL이나 쿼리 계약을 변경하지 않는다.
- 세미나 규약을 방문자용 화면에 전문으로 공개하지 않는다.
- 슬라이드 수, 글자 수 또는 섹션별 발표 시간을 고정하지 않는다.
- 미래의 재사용 가능성만으로 세미나 전용 구현을 전역 모듈로 승격하지 않는다.

## 4. 목표 아키텍처

```text
features/
└── seminars/
    ├── README.md
    ├── index.js
    ├── formats/
    │   └── introductory-60.md
    ├── data/
    │   ├── seminars.js
    │   ├── validation.js
    │   └── topics/
    ├── assets/
    │   └── <topic-id>/
    ├── components/
    ├── layouts/
    ├── services/
    │   └── pdf/
    ├── styles/
    └── tests/

pages/
├── seminars/
└── presentation/
```

### 소유권

- `pages/`는 URL 해석, DOM 마운트 지점과 기능 초기화만 담당한다.
- `features/seminars/index.js`는 페이지가 사용하는 공개 진입점이다. 페이지는 기능 패키지의 내부 파일을 직접 import하지 않는다.
- `formats/`는 세미나 형식별 사람용 규약을 소유한다.
- `data/`는 목록, 주제 원본과 데이터 검증을 소유한다.
- `assets/`는 저장소가 소유하는 주제별 이미지와 관련 에셋을 소유한다.
- `components/`는 목록, 헤더, 콘텐츠 블록과 사용자 상호작용을 소유한다.
- `layouts/`는 콘텐츠 블록을 발표 화면과 읽기 문서로 조립하는 표현 계약을 소유한다.
- `services/`는 PDF 생성과 인쇄 fallback처럼 UI 표현과 분리되는 세미나 전용 생명주기를 소유한다.
- `styles/`는 세미나 전용 화면과 출력 표현을 소유한다. 페이지는 기능 스타일 진입점을 명시적으로 불러온다.
- `tests/`는 데이터 계약, 렌더링, 상호작용과 출력 서비스의 세미나 전용 검증을 소유한다.

사이트 헤더, 디자인 토큰, 공통 레이아웃과 범용 HTML 유틸리티처럼 실제 비세미나 소비자가 있는 항목만 전역에 남긴다. 두 번째 실제 소비자가 생기기 전에는 공통화를 유예한다.

### 공개 경계와 URL

- `features/seminars/index.js`는 `initializeSeminarsPage`와 `initializePresentationPage` 두 오케스트레이터를 공개한다.
- 목록 페이지는 문서·창 참조만 전달하고, presentation 페이지는 문서·창 참조와 URL에서 읽은 `mode`, `topic`, `print` 값을 전달한다.
- 데이터 조회, 렌더러 선택, 헤더 구성, 제어기와 PDF 서비스 연결은 기능 패키지 내부에서 수행한다.
- 페이지나 전역 모듈은 기능 패키지의 데이터, 컴포넌트, 레이아웃 또는 서비스를 깊은 경로로 import하지 않는다.
- 세미나 목록: `/pages/seminars/`
- 발표 자료: `/pages/presentation/horizontal.html?topic=<id>`
- 읽기 자료: `/pages/presentation/vertical.html?topic=<id>`

URL은 이전 후에도 유지한다. 내부 import는 새 공개 진입점으로 한 번에 갱신하며 장기 호환 re-export를 두지 않는다. 규약 문서는 사이트 UI에서 링크하지 않는다. 이는 UI 비공개 원칙이며 직접 파일 접근을 막는 보안 경계는 아니다.

## 5. `introductory-60` 형식 계약

### 대상과 시간의 의미

- 대상은 관련 분야에 관심이 있지만 전문 배경지식은 없는 일반인이다.
- 선수 지식을 가정하지 않고 전문용어는 처음 등장할 때 일상 언어와 예시로 설명한다.
- `60분`은 대표적인 발표 상황을 나타내는 형식명이다. 콘텐츠 분량이나 발표자의 시간 배분을 제한하지 않는다.
- 발표자는 현장에서 강조와 생략을 조절할 수 있지만, 시간은 공통 원본이나 읽기 자료의 필수 내용을 제거하는 근거가 아니다.

### 필수 의미 구조

모든 `introductory-60` 주제는 다음 역할을 순서대로 한 번씩 가진다.

1. 문제의 정의: 무엇이 문제였고 왜 중요한지 설명한다.
2. 기존 접근: 이전에는 문제를 어떻게 이해하거나 해결했는지 설명한다.
3. 핵심 방법론: 현재의 핵심 원리와 해결 방식을 설명한다.
4. 활용 사례: 핵심 방법론이 실제로 어디서 어떻게 쓰이는지 연결한다.
5. 결론과 한계: 기억할 내용, 적용 범위와 한계를 정리한다.

역할명은 내부 작성 계약이다. 화면에 보이는 제목은 주제와 청중에 맞는 쉬운 질문이나 문장으로 바꿀 수 있다. 핵심 방법론이 가장 높은 설명 밀도와 깊이를 가지되, 다른 네 역할도 방법론의 필요성, 위치, 효용과 한계를 만드는 필수 맥락으로 유지한다.

### 공통 학습 성과

참석자와 독자는 자료를 접한 뒤 다음을 할 수 있어야 한다.

- 주제가 무엇이며 왜 등장했는지 설명한다.
- 핵심 개념과 개념 사이의 관계를 큰 그림으로 이해한다.
- 대표 사례를 핵심 원리와 연결한다.
- 기존 접근과 현재 방법의 차이 및 한계를 구분한다.
- 다음에 무엇을 더 학습할지 판단한다.

## 6. 공통 원본과 표현

세미나 한 개는 메타데이터, 다섯 의미 섹션, 식별 가능한 콘텐츠 블록과 발표 구성을 가진다.

### 메타데이터

- ID와 `introductory-60` 형식 식별자
- 제목, 부제, 요약과 태그
- 대상 독자와 선수 지식
- 학습 성과

### 콘텐츠 블록

초기 계약은 제목, 본문, 목록, 코드, 인용, 요약과 이미지를 명시적인 블록으로 지원한다. 각 블록은 주제 안에서 고유한 ID를 가지며 사실과 설명을 한 번만 소유한다. 슬라이드와 읽기 자료에 서로 다른 밀도가 필요하면 같은 블록 안에서 핵심과 상세 역할을 구분한다.

### 두 표현

- 읽기 자료는 다섯 의미 섹션과 필요한 원본 블록을 순서대로 모두 렌더링하며 발표 없이도 이해할 수 있어야 한다.
- 발표 자료는 별도의 발표 구성에서 원본 블록 ID를 참조해 슬라이드로 묶는다.
- 발표 자료를 위해 원본 사실을 복사하지 않고, 런타임 자동 요약이나 화면 크기에 따른 내용 삭제도 하지 않는다.
- PDF와 인쇄 결과는 각각의 발표·읽기 렌더러를 재사용한다.

## 7. 레이아웃과 에셋

### 발표 레이아웃

- 슬라이드 하나에는 하나의 주된 설명 목적을 둔다.
- 슬라이드 분할은 발표 시간이 아니라 가독성과 논리적 전환을 기준으로 한다.
- 경계를 넘는 콘텐츠를 자르거나 숨기지 않는다.
- 밀도가 높으면 글자를 과도하게 줄이지 않고 슬라이드를 나누거나 정보 구조를 바꾼다.
- 모바일에서는 발표 조작보다 자료 열람이 가능한 반응형 표현을 우선한다.

### 읽기 레이아웃

- 처음부터 끝까지 독립적으로 이해할 수 있는 연속 문서를 제공한다.
- 다섯 의미 단계와 제목 계층을 보존한다.
- 핵심, 상세 설명, 예시와 출처의 관계를 시각적으로 구분한다.
- 화면과 인쇄/PDF에서 내용이 누락되지 않게 한다.

### 이미지

이미지는 저장소 내부 경로와 의미를 설명하는 대체 텍스트를 가진다. 장식 이미지는 장식용임을 명시한다. 필요한 경우 캡션을 제공하고, 직접 제작물이 아니라면 출처와 권리 정보를 확인할 수 있게 기록한다.

슬라이드 수나 글자 수는 실패 조건이 아니다. 정량적인 밀도 검사는 작성자 경고로만 사용하고 실제 DOM overflow, 잘림, 누락과 접근성 계약 위반은 오류로 처리한다.

## 8. 검증과 오류 처리

자동 검증은 다음 오류를 배포 전에 차단한다.

- 형식 식별자 또는 필수 메타데이터 누락
- 다섯 의미 역할의 누락, 중복 또는 순서 오류
- 콘텐츠 블록 ID의 중복과 존재하지 않는 발표 참조
- 이미지 경로, 대체 텍스트 또는 장식 표시 누락
- 발표·읽기 렌더러의 공통 원본 계약 이탈
- PDF 성공·실패·fallback 경로의 임시 리소스 누수
- 모듈 경계와 파일 길이 정책 위반

개발과 테스트에서는 주제와 잘못된 필드 위치를 포함한 오류를 발생시킨다. 런타임에서는 일부 자료를 조용히 렌더링하지 않고 사용자에게 자료를 불러올 수 없다는 명시적인 상태를 보여준다.

브라우저 검증은 데스크톱과 모바일에서 목록, 두 표현, 주제·모드 이동, 키보드 조작, overflow, PDF 또는 인쇄 fallback과 콘솔 오류를 확인한다. 화면 동작이나 레이아웃을 변경하지 않는 설계·문서 단계에서는 브라우저 검증을 생략하고 그 이유를 이력에 기록한다.

## 9. 이전 전략

1. 실패하는 구조·계약 테스트로 목표 파일과 데이터 규칙을 먼저 고정한다.
2. `features/seminars/`의 공개 진입점과 데이터 검증기를 만든다.
3. Python·Web 주제를 공통 원본과 발표 참조 구조로 변환한다.
4. 목록, 콘텐츠 블록, 발표·읽기 레이아웃과 제어기를 이전한다.
5. PDF/인쇄 서비스와 세미나 전용 스타일을 이전한다.
6. 두 페이지가 기능 공개 API와 스타일 진입점만 사용하도록 바꾼다.
7. 모든 내부 소비자를 갱신한 뒤 구 파일을 제거하고 호환 re-export는 남기지 않는다.
8. 자동 테스트와 브라우저 회귀를 완료하고 정규 문서를 실제 구조로 갱신한다.
9. 이 설계 사양과 구현 계획의 보편적인 내용을 정규 문서에 흡수한 뒤 임시 문서를 제거한다.

부분 이전 상태는 장기 유지하지 않는다. 구현 중에는 `docs/status.md`에 현재 단계와 발견 문제를 기록한다.

## 10. 성공 기준

- 세미나 전용 구현과 테스트가 `features/seminars/` 안에 있고 페이지가 공개 API만 사용한다.
- 기존 세 URL 계약과 Python·Web 자료의 접근성이 유지된다.
- 두 주제가 `introductory-60`의 메타데이터, 다섯 의미 역할과 공통 원본 계약을 통과한다.
- 발표·읽기 자료가 원본 사실을 중복 소유하지 않는다.
- 이미지, 레이아웃, overflow와 오류 표시 계약이 자동 또는 브라우저 검증으로 확인된다.
- 전역에는 실제 공유 소비자가 있는 모듈만 남는다.
- `npm test`와 `git diff --check`가 통과한다.
- 관련 현재 문서와 `docs/history/2026.md`가 실제 구현과 검증 결과를 반영한다.

## 11. 규약 개선 원칙

실제 세미나를 만들며 발견한 마찰은 규약 개선 후보로 기록한다. 특정 주제의 예외인지 모든 `introductory-60` 세미나에 적용할 원칙인지 구분하고, 일반화할 근거가 있을 때만 형식 규약을 바꾼다. 현재 규약에는 최신 기준만 유지하고 변경 이유와 검증 결과는 연도별 이력에 보존한다.
