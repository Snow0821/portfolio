# Project Conventions

## 페이지

- 루트 `index.html` 외의 URL 진입 화면은 `pages/<page-name>/` 아래에 둔다.
- 페이지 패키지는 HTML, `page.js`, `page.css`를 기본 단위로 사용한다.
- `page.js`는 데이터 선택, URL 해석, 컴포넌트 조립과 생명주기 시작만 담당한다.
- 두 화면 이상에서 재사용하는 렌더링이나 상호작용은 `components/`로 승격한다.

## 컴포넌트와 서비스

- 컴포넌트는 특정 페이지 URL을 하드코딩하지 않고 입력으로 링크나 callback을 받는다.
- DOM 표현과 분리할 수 있는 기능은 `services/`에 둔다.
- 임시 DOM이나 외부 리소스를 만드는 서비스는 성공과 실패 모든 경로에서 정리한다.
- 세미나 PDF는 사용자가 해당 HTML 화면을 수동 인쇄하고 방향, 페이지 나눔, 잘림과 가독성을 시각 검토한 정적 파일만 공개한다.
- 실제 파일이 없으면 다운로드 링크를 만들지 않는다. 링크를 추가하기 전에 파일 존재, PDF 시그니처와 브라우저 다운로드를 확인한다.
- 데이터 모듈은 DOM, 페이지, 컴포넌트와 서비스에 의존하지 않는다.

## 모듈 경계와 크기

- 파일은 하나의 변경 이유와 하나의 주된 책임을 가져야 한다.
- 실행 JavaScript, CSS와 테스트 파일은 200줄 이하를 기본으로 한다.
- 201~300줄 파일은 `tests/module-policy.test.mjs`의 예외 목록에 경로와 응집된 상태를 유지해야 하는 구체적인 이유를 기록해야 한다. 300줄 초과 파일은 예외 없이 실패한다.
- 현재 예외 목록은 비어 있으며 파일 길이와 로컬 ES module 참조는 `npm test`에서 자동 검증한다.
- 콘텐츠 데이터, 문서, 연도별 이력과 생성 산출물은 줄 수 검사에서 제외한다. 다만 구조가 복잡해지면 책임 기준으로 나눈다.
- 짧은 코드를 작은 파일로 무조건 분산하지 않는다. 반복 사용, 독립 검증 또는 독립 변경이 가능한 경계가 있을 때 분리한다.
- 공개 함수는 이름과 입력만으로 계약이 충분히 드러나지 않을 때 짧은 JSDoc을 사용한다.

## 모듈 문서

- 파일이 세 개 이상이거나 공개 API, 생명주기, 오류 처리 또는 의존 방향이 코드만으로 명확하지 않은 기능 디렉터리는 `README.md`를 둔다.
- 모듈 README는 책임과 범위, 공개 계약, 내부 파일 역할, 허용 의존 방향, 오류 처리, 테스트 위치와 확장 규칙만 간결하게 설명한다.
- 단순 유틸리티나 자명한 단일 파일 모듈에는 별도 문서를 만들지 않는다.
- 코드와 문서가 어긋나지 않도록 모듈 경계를 변경하는 작업은 같은 작업에서 해당 README를 갱신한다.

## CSS

- 공통 의존 순서는 `tokens → base → layouts → components → page.css`다.
- 모든 화면은 `styles/main.css`를 먼저 사용한다.
- 같은 스타일이 두 페이지에서 필요하면 공통 레이아웃이나 컴포넌트 스타일로 옮긴다.
- `page.css`는 전역 태그의 기본 표현을 재정의하지 않는다.
- `!important`는 인쇄 매체처럼 우선순위 재정의가 불가피한 경우에만 사용한다.

## 접근성과 콘텐츠

- 아이콘만 있는 버튼은 동작 대상과 형식을 포함한 `aria-label`을 제공한다.
- 현재 페이지 링크에는 `aria-current="page"`를 사용한다.
- 제목 순서와 landmark를 유지하고, Markdown 문법을 HTML 텍스트에 그대로 넣지 않는다.
- 코드로 렌더링하는 일반 문자열은 신뢰된 로컬 데이터만 사용하며 외부 입력은 `innerHTML`에 직접 넣지 않는다.

## 세미나 작성

- `introductory-60`은 관련 분야에 관심이 있지만 전문 배경지식은 없는 일반인을 위한 개론형 세미나 형식이다. `60분`은 대표적인 발표 상황을 뜻하며 슬라이드 수, 글자 수, 자료 분량이나 섹션별 시간을 제한하지 않는다.
- 형식의 내부 의미 구조는 `문제의 정의 → 기존 접근 → 핵심 방법론 → 활용 사례 → 결론과 한계` 순서를 따른다. 화면 제목은 청중에게 자연스러운 표현으로 바꿀 수 있다.
- 핵심 방법론에 가장 높은 설명 밀도와 깊이를 두되 다른 네 역할도 필요성, 위치, 효용과 한계를 설명하는 필수 맥락으로 유지한다.
- 발표용 슬라이드와 읽기 자료는 식별 가능한 콘텐츠 블록의 공통 원본을 사용한다. 슬라이드는 원본 블록을 참조해 구성하고 읽기 자료는 발표 없이도 이해할 수 있는 세부 맥락을 보존한다.
- 발표 시간에 따른 현장 생략은 공통 원본이나 읽기 자료에서 필요한 내용을 제거하는 근거가 아니다.
- 정량적인 콘텐츠 밀도는 작성자 경고로만 사용하고 실제 overflow, 잘림, 누락과 접근성 위반은 오류로 다룬다.
- 수동 PDF의 파일명, 방향과 게시 전 검증은 `features/seminars/assets/pdf/README.md`를 단일 계약으로 사용한다.
- 세미나 규약은 내부 작성 계약이며 사이트 UI에 전문을 노출하지 않는다. 실제 제작에서 확인한 근거가 있을 때 현재 규약을 개선하고 변경 과정은 연도별 이력에 남긴다.

## 개발 환경과 검증

- Node.js 버전은 `.node-version`과 `package.json#engines.node`에서 `24.x`로 유지한다.
- 의존성 설치는 `npm install`, 구조와 동작 검증은 `npm test`를 사용한다.
- 정적 화면만 빠르게 확인할 때는 `python3 -m http.server 4173`을 사용할 수 있다.
- Vercel Functions까지 확인할 때는 `npm run dev:vercel`을 사용한다.
- `package.json#scripts.dev`에서 `vercel dev`를 호출하지 않는다. Vercel 통합 실행은 재귀 방지용 `dev:vercel` 스크립트를 유지한다.
- 새 동작이나 버그 수정은 실패하는 테스트를 먼저 확인한 후 최소 구현으로 통과시킨다.
- URL 진입점이나 CSS import를 바꾸면 존재하지 않는 로컬 참조와 금지된 레거시 경로가 없는지 자동 검증한다.

## 문서와 이력

- 현재 구조는 `architecture.md`, 규칙은 `conventions.md`, 장기 결정은 `decisions.md`, 진행 상태는 `status.md`에 유지한다.
- 프로젝트 파일을 변경한 작업은 `history/<year>.md`에 요청, 문제, 결정, 수행, 검증 결과와 남은 작업을 기록한다.
- 현재 문서에는 과거 설명을 누적하지 않고 대체된 내용은 연도별 이력에 보존한다.
- 작업마다 별도 로그나 ADR 파일을 만들지 않는다.
- 여러 세션이 필요한 설계나 구현 계획은 작업 중 임시 문서로 둘 수 있지만, 완료 전에 보편적인 내용은 현재 문서에, 수행 과정은 연도별 이력에 흡수하고 임시 문서를 제거한다.

## 작업 수행 순서

1. 파일 변경 전에 목표, 수행 항목과 성공 기준을 먼저 정한다.
2. 사용자의 제안에는 실행 전에 독립적인 기술 의견과 trade-off를 설명한다.
3. 작업 중 새로 발견한 문제를 해결 목록에 추가하고 `확인`, `해결`, `보류` 중 하나의 상태로 관리한다.
4. 해결한 문제는 원인과 해결 방법을 기록하고, 해결하지 못한 문제는 `docs/status.md`에 남긴다.
5. 완료 시 최초 계획, 문제와 해결, 실제 변경, 검증 결과와 남은 작업을 연도별 이력에 기록한다.
6. 여러 세션에 걸치는 작업은 `docs/status.md`를 최신 작업 목록으로 사용하고 완료된 과정은 이력으로 옮긴다. 프로젝트는 정규 문서와 모듈 README만 읽어도 이어서 작업할 수 있는 상태를 유지한다.
